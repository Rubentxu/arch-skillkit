# V2.5 Code Intelligence Provider Architecture

## 1. Problema

`CodeIndex` es útil, determinista y regenerable, pero no debe crecer hasta
convertirse en parser/compiler multilenguaje ni mezclar store, ingestion,
queries y lifecycle indefinidamente.

## 2. Port principal

```python
class CodeGraphQueryPort(Protocol):
    def resolve_symbol(self, ref: str) -> SymbolRef: ...
    def search_symbols(self, query: str, limit: int) -> list[SymbolRef]: ...
    def symbols_in_file(self, path: str) -> list[SymbolRef]: ...
    def dependencies(self, ref: SymbolRef) -> list[CodeEdge]: ...
    def dependents(self, ref: SymbolRef) -> list[CodeEdge]: ...
    def evidence_for(self, ref: SymbolRef) -> list[EvidenceRef]: ...
    def generation(self) -> CodeGeneration: ...
```

## 3. Separación interna

```text
EvidenceIngestor
  <- AstGrepProvider
  <- SemgrepProvider
  <- future SCIPProvider
  <- build metadata provider

EvidenceStore
  <- SQLiteEvidenceStore

CodeGraphQueryPort
  <- SQLiteCodeGraphQueries
```

`CodeIndex` puede mantenerse como compatibility facade durante la migración.

## 4. Provider provenance

Cada observation/edge indica:

- provider;
- provider version;
- sensor/rule;
- generation;
- precision class;
- origin;
- evidence fingerprint.

## 5. Precision classes

Sugerencia:

- `SYNTACTIC`: AST/pattern.
- `RULE_SEMANTIC`: Semgrep/contract rules.
- `COMPILER_SEMANTIC`: SCIP/compiler index.
- `BUILD_DECLARED`: manifests/build graph.
- `DECLARED`: usuario/policy.
- `INFERRED`: LLM.

Precision class no sustituye `confidence` ni `origin`.

## 6. SCIP

SCIP entra como provider opcional cuando exista indexador adecuado. Su valor es
aportar referencias/definiciones/relaciones obtenidas desde toolchains
semánticas sin que ArchSkillKit implemente un compilador.

## 7. Gate de utilidad

No se acepta un provider si no demuestra en fixtures:

- precision/recall superior o cobertura nueva;
- provenance estable;
- coste razonable;
- regenerabilidad;
- ausencia de mutación del repo.
