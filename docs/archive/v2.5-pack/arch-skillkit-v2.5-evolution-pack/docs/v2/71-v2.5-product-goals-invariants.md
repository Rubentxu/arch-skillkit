# V2.5 Product Goals and Invariants

## 1. Objetivos

### G1 — Evidence-grounded architecture

Toda afirmación arquitectónica significativa debe poder enlazarse a evidencia,
declaración explícita o inferencia versionada.

### G2 — Change intelligence

El usuario debe poder razonar sobre diferencias entre snapshots, blast radius,
staleness y policy impact sin reconstituir manualmente el estado.

### G3 — Agent-native bounded context

Los agentes reciben contexto limitado por presupuesto, versionado y stale-aware.

### G4 — Governance by construction

Un agente o viewer no puede convertir una propuesta en arquitectura aceptada
saltándose review/policy.

### G5 — Tool-first semantic precision

El kernel normaliza capacidades externas. No implementa compiladores
multilenguaje propios si una toolchain puede aportar datos precisos.

### G6 — Repository cleanliness

Analizar, visualizar o simular nunca modifica el source repository.

### G7 — Architectural integrity

Los boundaries hexagonales son ejecutables como gates y no sólo documentación.

## 2. Non-goals

- construir un IDE completo;
- sustituir compiladores, LSPs o static analyzers;
- crear un renderer gráfico propietario;
- introducir microservicios o infraestructura distribuida sin necesidad medida;
- usar consenso LLM como verdad;
- convertir el Architecture World en un log operacional;
- auto-promocionar conocimiento generado por LLM;
- imponer un único framework arquitectónico a proyectos analizados.

## 3. Invariantes del producto

`INV-01` mismo event log + misma code generation + mismas policies => mismo snapshot digest.

`INV-02` outputs externos semánticos incluyen `snapshot_id`.

`INV-03` una relación `DETECTED/high` mantiene evidence válida.

`INV-04` `INFERRED` nunca se serializa ni promociona como `DETECTED`.

`INV-05` LLM no muta main world por defecto.

`INV-06` projection files son derivados y recreables.

`INV-07` runtime PID/port/session no forma parte del Architecture World.

`INV-08` presentation edit no cambia semantic state sin candidate/review.

`INV-09` source repository before/after analysis permanece idéntico.

`INV-10` JSON públicos están versionados por schema.

`INV-11` una UAT declarada determinista registra inputs, outputs y hashes.

`INV-12` delivery adapters son siblings: ninguno usa otro como API.

`INV-13` Application API no depende de tecnología de delivery o persistencia.

`INV-14` ActiveGraph permanece detrás de un outbound adapter/ACL.

`INV-15` una baseline de deuda arquitectónica no puede crecer silenciosamente.

`INV-16` la misma entrada a un deterministic gate genera mismo verdict y findings ordenados.

`INV-17` un waiver tiene owner, rationale, scope y expiry.

`INV-18` ArchitectureDelta puede explicar por qué cambió el resultado del gate.

## 4. Regla de evolución

Una feature futura entra en roadmap sólo si mejora al menos una de:

- grounding;
- explainability;
- change intelligence;
- context efficiency;
- governance;
- interoperability;
- deterministic learning.

Si sólo aumenta superficie sin mejorar uno de esos ejes, se aplaza.
