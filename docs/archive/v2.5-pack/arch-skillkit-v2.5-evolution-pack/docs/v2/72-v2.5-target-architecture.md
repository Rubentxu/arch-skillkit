# V2.5 Target Architecture

## 1. Estilo

- Hexagonal architecture.
- Graph-native domain semantics.
- Event-sourced Architecture World.
- CQRS ligero: queries/commands diferenciados sin infraestructura CQRS obligatoria.
- Thin inbound adapters.
- Explicit outbound ports.
- Composition Root único.
- Reactive behavior sólo para causalidad real.

## 3. Regla de dependencias

```text
delivery -> application -> domain
                         -> ports
adapters/outbound -> ports/domain contracts
bootstrap -> todos para wiring
```

Prohibido:

```text
application -> delivery
application -> activegraph
application -> sqlite3
application -> concrete CodeIndex
application -> world implementation
delivery/http -> delivery/cli
delivery/mcp -> delivery/cli
```

## 4. Composition Root

`bootstrap/application.py` es la única autoridad para construir el runtime por
repositorio.

Conceptualmente:

```python
app = ArchSkillKitApplication.for_repo(repo_path)

app.status(...)
app.explain(...)
app.impact(...)
app.delta(...)
app.proposals.create(...)
app.proposals.review(...)
app.proposals.promote(...)
app.simulate(...)
```

Los adapters no construyen manualmente world/index/store.

## 5. Domain vs engine

El dominio es graph-native: conoce elementos, relaciones, eventos, snapshots,
forks y causalidad. No conoce `activegraph.Graph`, `Runtime`, store URL ni API
concreta del engine.

## 6. Estado

### Architecture World — durable semantic state

- accepted knowledge;
- evidence links;
- rules;
- proposals/reviews;
- waivers/debt;
- auditable candidate knowledge.

### Code/Evidence Store — regenerable

- files;
- symbols;
- semantic/syntactic edges;
- evidence records;
- provider provenance;
- scan generations.

### RunLedger — durable operational metadata

- run IDs;
- timings;
- tool versions;
- snapshot hashes;
- artifact hashes;
- metrics.

### RuntimeRegistry — ephemeral

- PIDs;
- ports;
- viewer sessions;
- locks.
