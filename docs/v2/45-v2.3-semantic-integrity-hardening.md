# V2.3 — Semantic Integrity & Architectural Hardening

Iniciativa de endurecimiento arquitectónico y semántico derivada de la
[auditoría de septiembre 2026](44-architecture-review-2026-09.md). No añade
features de producto: convierte en reales los límites ya diseñados,
fortalece la semántica de facts/evidencia y elimina las duplicaciones de
conocimiento.

Estado: propuesta. Plan de ejecución: [46-roadmap-v2.3.md](46-roadmap-v2.3.md).

## 1. Objetivos y no-objetivos

### Objetivos

1. Corregir los cinco P0 de dominio verificados en la auditoría.
2. Hacer hexagonal lo que ya *dice* ser hexagonal (puertos reales, sin
   `world.graph` fuera del adapter).
3. Sustituir contratos implícitos (strings, nombres, posiciones) por
   contratos explícitos (`SensorContract`, `EvidenceId`, `ScanGeneration`,
   `ProjectContext`).
4. Establecer un quality gate Python con tests de propiedad.
5. Dogfooding: ArchSkillKit verificando su propia arquitectura como gate.

### No-objetivos

- Reescribir el modelo de dos grafos, ActiveGraph o el Context Compiler.
- Embeddings / vector DB / RAG en el Context Compiler.
- Terminar los proyectores de V2.2 en esta iniciativa (llegan *después* del
  hardening, en orden GraphML → JSON Canvas → draw.io).
- SOLID por ceremonia: no se parte `ArchitectureWorld` en veinte servicios.

## 2. Conceptos transversales

Cuatro conceptos nuevos eliminan la mayor parte de la connascence
detectada. Ninguno requiere reescritura: son introducciones incrementales.

### 2.1 `ProjectContext` — identidad resuelta una vez

```python
@dataclass(frozen=True)
class ProjectContext:
    project_id: str
    repository_root: Path
    workspace: Path

    @classmethod
    def for_repo(cls, repo_path: str | Path) -> "ProjectContext": ...
```

Hoy `CodeIndex.for_repo()` construye un `ArchitectureWorld` solo para
obtener el workspace (dependencia invertida, P1-1). Con `ProjectContext`,
ambos dominios dependen de un valor de identidad compartido:

```text
        ProjectContext
         /          \
ArchitectureWorld   CodeIndex
```

`ids.py` deja de ser API pública de dominio y pasa a ser detalle de
construcción del contexto.

### 2.2 `SensorContract` — reglas autodescriptivas

Las reglas Semgrep declaran el hecho que producen; Python interpreta un
contrato genérico. Desaparecen `_EDGE_RULES` y el «primer literal
encontrado»:

```yaml
# rules/semgrep/kotlin/spring-messaging.yml (extracto)
rules:
  - id: arch.kotlin.spring.publishes-topic
    metadata:
      archskillkit:
        fact: publishes            # predicate semántico
        subject_metavar: $SVC      # símbolo contenedor
        target_metavar: $TOPIC     # argumento del hecho
        target_kind: topic
        cardinality: many          # ONE | many — drive de contradicciones
        confidence: high
    patterns: ...
```

Ganancias en cascada:

- **P0-3**: contradicción solo con `cardinality: one`; `publishes`,
  `exposes` o `depends_on` múltiples dejan de ser contradicciones.
- **P1-5**: el naming de reglas deja de estar acoplado al intérprete.
- **Sensor packs**: paquetes de reglas por framework/stack (spring, ktor,
  axum, kafka, sqlx, nestjs…) publicables e instalables sin tocar el core.
  El contrato (`archskillkit.metadata`) es la única interfaz.

El validador de contratos vive en el paquete (`archskillkit sensors
validate rules/`) para que una regla mal declarada falle en el scan, no en
el ingest.

### 2.3 `ScanGeneration` — generaciones de scan atómicas

Estado actual: `files.path UNIQUE` + `INSERT OR IGNORE` ⇒ un scan nuevo no
sustituye los hechos del anterior (P0-1). Diseño:

```sql
scan_generation(id INTEGER PRIMARY KEY,
                run_id TEXT NOT NULL,
                created_at TEXT NOT NULL,
                status TEXT NOT NULL)   -- staging | current

files / symbols / edges  →  + generation_id INTEGER NOT NULL
```

Ingest: escribir la generación N en staging → promoción atómica
(`current = N`, purga de generaciones antiguas). Invariante:

```text
index(generación N) contiene exactamente los hechos del scan N
```

Efecto compuesto: `diff(generación N-1, N)` produce *semantic deltas*
(edges añadidos/eliminados, endpoints cambiados, datastore/topic/client
nuevos) que alimentan el drift real (P1-8) — el drift pasa de «revalidar
políticas del modelo» a «evaluar el delta de código contra la arquitectura
aceptada».

### 2.4 `EvidenceId` — evidencia content-addressed

```python
EvidenceId = sha256(f"{commit}|{file}|{start}|{end}|{sensor}|{rule}|{fingerprint}")
```

El Code Index conserva `match_start/match_end` del match real, separados
del `container_symbol`. La promoción referencia por `EvidenceId`, no por
`(rule, file, source_start_line)`. Mejora: provenance, stale detection
(precisión de línea), dedup, diff y auditoría. Además elimina
`_MAX_CONTAINER_DISTANCE = 2`: el owner del hecho se resuelve como el
*smallest symbol range containing the match* usando los ranges que ast-grep
ya entrega (P1-7).

## 3. Catálogo de tests de propiedad

Estos invariantes habrían detectado todos los P0 de la auditoría. Con
`hypothesis` sobre generadores de grafos/índices sintéticos:

| # | Propiedad | Detecta |
|---|---|---|
| PR-1 | `edge A→B ⇒ path(B, A) is None` salvo camino propio | P0-2 dirigido |
| PR-2 | `index(gen N+1)` contiene exactamente los hechos de N+1 | P0-1 staleness |
| PR-3 | `promote(main, p) ⇒ structural_diff(main, p).is_empty()` | P0-4 promoción |
| PR-4 | edición manual del artefacto ⇒ regenerar sin `force` falla | P0-5 protección |
| PR-5 | dos hechos con `cardinality: many` e igual sujeto ⇒ nunca contradicción | P0-3 semántica |

PR-3 es el invariante fuerte que el review externo pide y la auditoría
confirma ausente: la promoción debe ser un *fixpoint* del diff.

## 4. Límites hexagonales objetivo

Sin big-bang. Evolución hacia:

```text
CLI
 │ adapters (argparse → use case calls)
 ▼
USE CASES
  Discover · Context · Project · Review · Drift · Proposal
 │
 ▼
PORTS
  ArchitectureWorldPort · CodeIndexPort · ProjectionPort
 │
 ▼
ADAPTERS
  ActiveGraphWorldAdapter · SQLiteCodeIndex · likec4/arrows/graphml/…
```

Reglas de dependencia (verificables por dogfooding, ver §5):

1. Los use cases no importan ActiveGraph ni sqlite3.
2. `promotion`/`proposals` no tocan `world.graph`; usan operaciones de
   puerto (`record_observation`, `create_claim`, `accept_claim`, `fork`,
   `remove_relation`, …).
3. `_run_exists()` y cualquier conocimiento del esquema interno de
   ActiveGraph quedan dentro del adapter.
4. `CodeIndex` deja de conocer `ArchitectureWorld` (P1-1 → `ProjectContext`).

Split moderado de `world.py`: facade delgada + `ClaimRepository`,
`ArchitectureRepository`, `ArchitecturePolicyService`, `ProposalService`.
Los use cases (`discover`, `review`, `drift`, `promote`, `context`) ya
existen como funciones; se mantienen como capa de orquestación.

## 5. Dogfooding como fitness functions

ArchSkillKit se analiza a sí mismo en cada gate (release y, si se decide,
PR CI). Las reglas del propio proyecto se convierten en las constraints
arquitectónicas del repo:

| Fitness function | Regla |
|---|---|
| `python/src/archskillkit/domain**` MUST NOT import `activegraph` | ADR-0024 real |
| `promotion.py` / `proposals.py` MUST NOT call `world.graph` | encapsulación |
| `codeindex.py` MUST NOT import `world` | P1-1 |
| `projections/adapters/*` MUST declare `ProjectionAdapter` contract | OCP |
| CLI MUST NOT call private domain methods (`_`-prefixed) | SRP CLI |
| analyzed repository MUST remain unchanged | golden rule |

Implementación: job del gate que ejecuta `archskillkit scan` sobre el propio
repo con el pack `arch.archskillkit-self` y evalúa las reglas como
`architecture_rule` del drift determinista. El producto vigila su propia
arquitectura con su propio mecanismo.

## 6. Fuente única de versión

Hoy coexisten pyproject, `version.json`, el tag Git y menciones manuales en
STATUS/README (Connascence of Value). Decisión: **pyproject es la fuente**;
`version.json` se genera (`scripts/release/sync-versions.py`) y el toolchain
matrix se mantiene como contrato separado (no es SemVer del paquete).
STATUS/README no declaran versiones: enlazan a la fuente.

## 7. Quality gates

- `ruff` (lint + format) — sin burocracia, reglas base.
- `mypy` en modo progresivo (strict en paquetes nuevos: `sensors`,
  `generations`).
- `pytest-cov` con umbral informado (no bloqueante hasta V2.3-8).
- `hypothesis` para el catálogo §3.
- Dogfooding (§5) como gate adicional.

## 8. Orden de V2.2 tras el hardening

1. **GraphML** — un adapter desbloquea Cytoscape, Gephi y yEd; natural desde
   `code.sqlite`.
2. **JSON Canvas** — formato trivial; encaja con knowledge maps del world.
3. **draw.io** — XML + layouts + edición estable: el más complejo, al final.

Los tres implementan `ProjectionAdapter` y heredan gratis la protección
real de ediciones manuales (P0-5 corregido) y el lifecycle de V2.2.
