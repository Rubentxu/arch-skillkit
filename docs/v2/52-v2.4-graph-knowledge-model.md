# V2.4 Graph Knowledge Model

## 1. Principio

**Graph semantics everywhere; one physical graph database nowhere required.**

La ontología, provenance, causality y temporalidad se expresan como objetos/relaciones. El almacenamiento se especializa por carga:

- Code Index: SQLite/índices regenerables para millones de símbolos;
- Architecture World: ActiveGraph event log + materialización;
- RunLedger: store operacional indexado;
- artifacts: filesystem/XDG + manifests.

## 3. Origin y epistemic status

Mantener `DETECTED`, `INFERRED`, `DECLARED`, `OBSERVED`.

Separar tres ejes:

```text
origin      = cómo nació
confidence  = fuerza de soporte
status      = lifecycle/gobernanza
```

`status` recomendado:

- CANDIDATE;
- REVIEW_REQUIRED;
- ACCEPTED;
- REJECTED;
- SUPERSEDED;
- STALE;
- WAIVED.

Un objeto puede ser `INFERRED`, confidence `0.96` y seguir `CANDIDATE`.

## 4. Stable references hacia CodeIndex

No duplicar symbols completos. Introducir referencias estables:

- `FileRef`;
- `CodeSymbolRef`;
- `EndpointRef`;
- `ConfigRef`;
- `BuildTargetRef`.

Estas referencias incluyen generation/identity suficiente para resolverlas mediante `CodeGraphQueryPort`.

## 5. KnowledgeGap

Debe ser first-class porque el producto necesita modelar lo desconocido:

```yaml
id: kg-001
question: Who consumes PaymentCreated?
impact: high
status: open
related_elements: [payment-service, payment-created]
candidate_answers: []
evidence_needed:
  - kafka consumer registrations
  - topic configuration
```

Puede activar un Evidence Scout sólo si su impacto/prioridad lo justifica.

## 6. Evidence freshness

Evidence debe poder relacionarse con:

- scan generation;
- commit;
- source range;
- sensor revision;
- content digest.

Cambio de generation puede marcar Evidence stale; un relation behavior puede recalcular claims relacionados.

## 7. Temporal lineage

Consultas objetivo:

- `why(element|relation|claim)`;
- `when(relation)`;
- `changes(since snapshot)`;
- `architecture_blame`;
- `first_seen` / `last_seen`;
- `superseded_by`.

## 8. Graph-derived analytics

Candidates útiles:

- architectural centrality;
- boundary crossing count;
- evidence density;
- unknown density;
- relation churn;
- architecture hotspot score;
- ownership concentration;
- dependency blast radius;
- evidence age distribution.

No convertir heurísticas en verdad de dominio sin validación.

## 9. Future materialization

Si el Architecture World supera la capacidad práctica del store inicial, evaluar un GraphStore reconstruible (p.ej. FalkorDB) detrás de un port de lectura. El event log sigue siendo source of truth.
