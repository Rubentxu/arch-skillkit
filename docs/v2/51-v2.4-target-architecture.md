# V2.4 Target Architecture

## 1. Architectural style

- Hexagonal architecture.
- ActiveGraph event-sourced domain runtime.
- Application API use cases separados de delivery adapters.
- Graph-native semantics con persistencia física especializada.
- Reactive behaviors sólo cuando existe semántica reactiva real.

## 5. Tres dominios de estado

### ArchitectureWorld — durable domain state

Contiene knowledge, evidence links, accepted architecture, proposals, reviews, policies, waivers, agent candidate knowledge cuando sea relevante para auditoría.

### RunLedger — durable operational history

Contiene runs de ingest/discover/drift/project/gate/investigation:

- commit;
- timestamps;
- timings;
- metrics;
- artifact hashes;
- snapshot digests;
- tool versions.

No debe inflar el domain graph con logs operativos de bajo nivel.

### RuntimeRegistry — efímero

Ubicación recomendada: `$XDG_RUNTIME_DIR/archskillkit/...` con fallback seguro.

Contiene:

- viewer sessions;
- PIDs;
- local ports;
- embedded/control-plane sessions;
- lock files.

Nunca guardar PIDs como ArchitectureWorld events.

## 6. ArchitectureSnapshot

Objeto inmutable derivado:

```text
ArchitectureSnapshot
  snapshot_id/digest
  project_revision
    git_commit
    dirty_digest
  code_revision
    scan_generation
    sensor_pack_revisions
  world_revision
    last_event_id
    event_log_digest
  policy_revision
  knowledge
    element_count
    relation_count
    evidence_coverage
    unknowns
  drift
  fitness_profile
  capability_manifest
  artifact_manifest
```

Todas las surfaces externas deben poder incluir `snapshot_id`.

## 7. ActiveGraph boundary

Mantener ActiveGraph detrás de adapters/repositories/domain services. La semántica del proyecto sí es ActiveGraph-first, pero los use cases no deben depender de APIs concretas del engine.

No sobreabstraer: la meta es evitar connascence estructural con `world.graph.*`, no ocultar que el producto usa event sourcing y object graphs.

## 8. Reactive design

Usar behaviors para relaciones causales claras:

```text
scan.completed -> ingest evidence
claim.changed -> evaluate support/contradiction
accepted claim -> architecture mapper
architecture changed -> projection staleness
stale evidence -> confidence recomputation
knowledge gap -> optional evidence scout
high-impact conflict -> optional second reviewer
```

No usar behaviors para emular una secuencia procedural que sería más clara como use case síncrono.
