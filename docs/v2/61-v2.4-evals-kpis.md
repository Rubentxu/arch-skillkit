# V2.4 Evals and KPIs

## 1. Principio

Medir utilidad y grounding, no cantidad de features ni “inteligencia” percibida.

## 2. Context KPIs

- estimated tokens vs naive baseline;
- source bytes read;
- source lines emitted;
- budget adherence;
- evidence density;
- cache hit rate;
- relevant fact recall en fixtures.

`source_file_reads` se conserva por compatibilidad pero no es KPI suficiente.

## 3. Knowledge quality

- grounding rate: candidate claims con evidence refs válidas;
- unsupported claim rate;
- relation precision/recall;
- contradiction recall;
- accepted candidate rate;
- rejected candidate rate;
- stale candidate rate;
- unresolved knowledge gaps.

## 4. Architecture model KPIs

- evidence coverage;
- mapped architecture surface;
- unclassified dependency count;
- boundary coverage;
- unsupported construct count;
- relation churn;
- architecture delta size;
- drift MTTR.

## 5. Agent efficiency

- accepted facts per 1k tokens;
- evidence requests per solved gap;
- tool calls per investigation;
- targeted source bytes vs repo size;
- stale-session recoveries;
- second-opinion trigger rate.

## 6. Prompt/Skill evals

Cada PromptRevision/SkillRevision se evalúa sobre fixtures versionados.

Comparar:

- graph edit distance vs expected subgraph;
- exact schema validity;
- evidence reference validity;
- knowledge gap correctness;
- stability across repeated runs/fixtures;
- cost/tokens.

## 7. Multi-model eval

No usar consenso como verdad. Medir:

- agreement/disagreement graph deltas;
- evidence overlap;
- unique supported claims;
- unsupported unique claims.

Second opinion sólo para policies de riesgo definidas.

## 8. Projection evals

- schema validity;
- semantic object preservation;
- metadata/provenance preservation;
- layout/readability human review sample;
- external consumer open success;
- round-trip classification accuracy presentation vs semantic.

## 9. Sensor distillation KPIs

- candidate frequency;
- deterministic sensor precision;
- recall;
- false positive rate;
- false negative rate;
- LLM calls avoided after sensor adoption;
- token/cost reduction;
- regression across language/framework fixtures.

## 10. Fitness Score policy

Si se ofrece score:

- fórmula publicada;
- dimensiones N/A no equivalen a cero;
- versionar fórmula;
- no usarlo como único release gate;
- evitar cambiar weights sin golden/history migration note.
