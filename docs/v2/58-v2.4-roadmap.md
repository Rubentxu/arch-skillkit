# V2.4 Roadmap

## Estrategia

El roadmap está diseñado para validar arquitectura emergente. Cada milestone tiene un gate observable; no avanzar por calendario si el gate muestra connascence, coste o falta de valor.

## M0 — Product Kernel & Boundaries

Objetivo: crear contratos que eviten construir `status/view/MCP/serve` directamente encima del CLI/world actual.

Deliverables:

- nomenclatura V2.4 y docs/STATUS alineados;
- `ArchitectureSnapshot`;
- `RunLedger`;
- `RuntimeRegistry`;
- typed action suggestions;
- split mínimo de query/mutation/governance ports;
- Application API skeleton;
- command handlers desacoplados del `cli.py` God Object;
- Architecture Coverage/Unknowns baseline;
- completar/registrar plan Axum + Django OSS.

Gate:

- CLI actual sigue green;
- snapshot reproducible para mismo event log/generation;
- PID/runtime state no aparece en world event log;
- al menos status puede implementarse sin import directo de CLI desde MCP/HTTP futuros.

## M1 — Daily Driver & Viewer Foundation

Deliverables:

- `ark status`;
- `ark schema`;
- `ark explain/why`;
- `ark view`;
- ViewerDescriptor/Registry/Router;
- `ark viewers` + doctor capability manifest;
- LikeC4 managed server/webcomponent proof;
- draw.io embed proof;
- SystemDefaultViewer;
- multi-viewer capability matrix actualizada;
- Excalidraw adapter spike decision.

Gate:

- un artifact se genera aunque no exista viewer;
- GraphML abre en al menos un viewer externo real;
- draw.io round-trip separa presentation vs semantic candidate;
- explain reconstructs evidence lineage.

## M2 — Change Intelligence & Agent Context

Deliverables:

- typed `ContextQuery`;
- Context Compiler metrics reforzadas;
- Prompt Compiler;
- `ark ask`;
- `ark impact`;
- KnowledgeGap/EvidenceRequest;
- `AgentSession`;
- agent bootstrap context;
- skills `arch-investigation` y `arch-reviewer`.

Gate:

- agent can solve defined architecture questions with bounded context;
- stale session detected;
- evidence density and token metrics measured against naive baseline;
- source read policy remains targeted.

## M3 — Governance & CI

Deliverables:

- run history;
- ArchitectureDelta;
- Fitness Profile;
- aggregate score optional;
- `ark gate`;
- waivers/debt ledger;
- SARIF + Markdown + JSON reports;
- PR delta;
- signed snapshot/attestation spike.

Gate:

- same inputs -> identical deterministic gate result;
- explicit dimensions have N/A semantics;
- expired waiver fails configured gate;
- SARIF accepted by validator/consumer.

## M4 — Agent-Native Distribution

Deliverables:

- MCP adapter compatible with selected 2026-07-28 SDK line;
- read/propose/admin capability tiers;
- resources/prompts/tools;
- explicit AgentSession handles;
- embedded `arch-llm` optional pack;
- candidate knowledge workflow;
- `simulate/guard`;
- multi-model second opinion only under policy.

Gate:

- same explain/impact/context result shape via CLI and MCP;
- MCP default cannot promote;
- candidate LLM claim requires review/policy before accepted world;
- replay fixture without API key.

## M5 — Control Plane & Projection Intelligence

Deliverables:

- local control plane shell;
- snapshot selector;
- architecture/evidence/unknowns panels;
- viewer embedding/launch;
- LikeC4 + draw.io + Excalidraw where accepted;
- projection enrichment overlays;
- governance/investigation UI;
- run trace UI.

Gate:

- Control Plane contains no proprietary graph renderer;
- disabling embedded viewer leaves export/open workflow functional;
- semantic edits become proposals, never direct accepted changes;
- 127.0.0.1/read-only default security gate.

## M6 — Learning Architecture

Deliverables:

- SensorCandidate;
- sensor distillation workflow;
- conformance mining;
- ArchitectureRuleCandidate;
- OntologyProposal;
- prompt/skill/model graph evals;
- optional incremental/watch based on measured need.

Gate:

- at least one repeated LLM inference converted to deterministic sensor with positives/negatives;
- no regression on existing OSS fixtures;
- measured cost reduction for the learned pattern.

## Release strategy

No forzar un único SemVer para toda V2.4. Cortar releases pequeños después de gates útiles (p.ej. M0/M1, M2, M3) y registrar qué milestones incluye cada release.
