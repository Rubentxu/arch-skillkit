# V2.4 Product Specification

## 1. Jobs to be done

### Arquitecto / senior engineer

- entender arquitectura real sin leer el repositorio completo;
- preguntar “por qué existe esta relación” y obtener evidencia;
- comparar arquitectura entre commits/runs;
- investigar zonas de alta incertidumbre;
- validar propuestas antes de modificar código;
- producir vistas adecuadas para distintas audiencias y herramientas.

### Coding agent

- obtener una constitución arquitectónica compacta;
- conocer boundaries, policies y restricciones;
- consultar impacto antes de editar;
- recibir contexto versionado y limitado por budget;
- proponer cambios sin escribir conocimiento aceptado directamente;
- detectar que su contexto ha quedado stale.

### CI/CD

- ejecutar gates deterministas;
- bloquear nuevo drift o violaciones explícitas;
- emitir SARIF/Markdown/JSON;
- comparar delta arquitectónico base vs head;
- registrar snapshots y attestations.

### Reviewer / maintainer

- revisar candidate knowledge;
- distinguir detected/inferred/declared/observed;
- aceptar excepciones con owner/rationale/expiry;
- auditar qué prompt/skill/model/evidence produjo un claim.

## 2. Capabilities

### 2.1 State Intelligence

`status` produce un `ArchitectureSnapshotSummary` y typed action suggestions. No devuelve comandos shell como semántica primaria.

Cada suggestion incluye:

- `action_id`;
- `reason_code`;
- `parameters` tipados;
- preconditions;
- mutation scope;
- risk;
- expected effects.

El renderer CLI puede mostrar el comando equivalente.

### 2.2 Explainability

`explain`/`why` reconstruye lineage:

```text
commit -> observation -> evidence -> inference -> claim -> relation -> finding/projection
```

Debe responder también qué se desconoce y qué evidencia falta.

### 2.3 Impact intelligence

`impact <file|symbol|element>` devuelve:

- dependientes directos/transitivos;
- blast radius arquitectónico;
- interfaces afectadas;
- policies potencialmente afectadas;
- evidence/claims que quedarían stale;
- ContextPack de cambio.

Debe implementarse antes de features puramente estéticas de trend.

### 2.4 Ask

`ask` es sugar de lenguaje natural sobre `ContextQuery`, no un chatbot.

Debe existir equivalente tipado:

```text
ark ask --intent endpoints --subject Orders
```

La salida nunca se convierte automáticamente en conocimiento.

### 2.5 Governance

- drift determinista;
- proposals por fork/diff;
- waivers con expiry;
- gates explícitos;
- SARIF;
- simulate/guard counterfactual;
- architecture debt ledger.

### 2.6 Projections & Viewers

La generación de artefactos es independiente de su aplicación consumidora.

Formatos iniciales:

- LikeC4;
- Arrows;
- draw.io;
- JSON Canvas;
- GraphML;
- Excalidraw (V2.4 candidate);
- Mermaid/DOT/D2/PlantUML como derived/transcoded candidates cuando aporte valor.

Viewer modes:

- EMBEDDED;
- MANAGED_SERVER;
- LOCAL_PROCESS;
- WEB_HANDOFF.

### 2.7 Agent Intelligence

Los LLM producen `InferenceCandidate`, `Hypothesis`, `KnowledgeGap`, `EvidenceRequest`, `ProjectionEnrichment`, `ArchitectureRuleCandidate` y `SensorCandidate`.

No producen mutaciones aceptadas directas.

### 2.8 Temporal Intelligence

- `history`;
- `changes --since`;
- `when`;
- `blame-architecture`;
- future `bisect drift`.

## 3. Product invariants

1. Todo externally-visible claim importante identifica el snapshot del que procede.
2. Una relación automática `high` conserva Evidence.
3. Un `INFERRED` nunca se trata como `DETECTED`.
4. Un LLM no puede promover main world por defecto.
5. Projection files son recreables; borrarlos no destruye conocimiento.
6. PIDs/ports no son eventos de dominio arquitectónico.
7. Presentation state no cambia semantic state sin import/review explícito.
8. El source repository permanece intacto.
9. El grafo describe tanto conocimiento como incertidumbre relevante.
10. Outputs JSON tienen schema versionado.

## 4. Definition of done de producto V2.4

V2.4 se considera funcional cuando una persona y un agente externo pueden:

1. bootstrappear un repo real;
2. obtener snapshot/status;
3. explicar un elemento con evidence;
4. medir coverage/unknowns;
5. ejecutar impact;
6. producir al menos tres proyecciones y abrirlas en viewers distintos;
7. crear una investigación LLM cuyo resultado quede como candidate knowledge auditable;
8. promover sólo mediante policy/review;
9. ejecutar gate PR con delta + SARIF;
10. consumir las mismas capacidades por CLI y MCP;
11. reconstruir el mismo snapshot mediante replay.
