# V2.4 Context and Prompt Compiler

## 1. Objetivo

El LLM nunca recibe “el repositorio” ni “todo el grafo”. Recibe un contexto compilado, versionado, presupuestado y trazable para una tarea concreta.

La pipeline objetivo es:

```text
Task / Question
      |
      v
Intent Resolver
      |
      v
Context Compiler
  | Architecture World
  | CodeGraphQueryPort
  | Evidence
  | Knowledge Gaps
      |
      v
ContextPack
      |
      +--> PromptSpec
      +--> AgentRole
      +--> OutputSchema
      |
      v
Prompt Compiler
      |
      v
CompiledPrompt / MCP context / CLI markdown
```

## 2. ContextQuery

No depender de una pregunta NL. Modelo mínimo:

```yaml
intent: impact|explain|endpoints|drift|evidence|projection|review|custom
subject:
scope:
goal:
changed_files: []
budget:
  max_nodes:
  max_edges:
  max_source_lines:
  max_estimated_tokens:
include_unknowns: true
include_history: false
```

`ark ask` traduce NL a `ContextQuery`; agentes avanzados pueden construirlo directamente.

## 3. Ranking

Continuar aprovechando:

- graph distance;
- subject/goal terms;
- changed-file proximity;
- recent generation delta;
- evidence quality;
- architecture centrality;
- relation degree.

Añadir:

- uncertainty reduction potential;
- policy relevance;
- boundary crossings;
- impact relevance;
- stale evidence penalty;
- duplicate-information penalty.

## 4. Métricas correctas

No usar `source_file_reads` como único KPI porque leer un fichero completo para emitir un snippet pequeño puede ocultar coste.

Registrar:

- candidate source files;
- source files opened;
- source bytes read;
- source lines read;
- source lines emitted;
- estimated input tokens;
- nodes/edges included;
- budget utilization;
- evidence items;
- evidence-backed facts;
- evidence density (facts/1k tokens);
- cache hit rate.

## 5. Targeted source read

Orden:

```text
Architecture/Evidence query
  -> CodeIndex
  -> exact FileRef/SymbolRef/range
  -> source snippet
```

Evitar recursive browsing.

Optimización futura: lectura parcial real por offsets/ranges cuando el actual `read_text()` completo sea un bottleneck medido.

## 6. ContextPack lifecycle

Cada ContextPack contiene:

- `context_pack_id`;
- snapshot_id;
- query digest;
- compiler version;
- budget;
- selected refs;
- uncertainties;
- metrics;
- content digest.

Puede persistirse como artifact/referencia, no necesariamente como nodos voluminosos en el domain graph.

## 7. PromptSpec

Debe contener:

- name/version/hash;
- role;
- objective;
- constraints;
- accepted input intents;
- required capabilities;
- output schema;
- safety/policy notes.

No duplicar architecture knowledge dentro del prompt.

## 8. Structured outputs

Todo behavior LLM de dominio usa schema Pydantic/JSON Schema.

Nunca parsear prose heurísticamente si puede pedirse:

```yaml
hypotheses: []
claims: []
knowledge_gaps: []
evidence_requests: []
uncertainties: []
```

## 9. Cache/replay

Clave candidata:

```text
prompt_hash + context_pack_hash + model_contract + tool_policy_revision
```

Los fixtures de LLM permiten UAT determinista sin API key. Replay debe detectar divergencia si cambia prompt hash/schema/policy.

## 10. Information gain

Evidence Scout puede rankear acciones por heurística:

```text
utility = expected_uncertainty_reduction / estimated_cost
```

No se exige un modelo probabilístico sofisticado en V2.4. Empezar con categorías `low|medium|high` y medir.
